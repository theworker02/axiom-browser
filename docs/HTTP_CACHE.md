# HTTP Cache (Phase 3 Wave E)

`axiom_net::HttpCache` is a private (per-profile) HTTP cache implementing a subset of RFC 9111. Every profile owns exactly one cache, created by its `NetworkService`. Caches are never shared between profiles.

## Where the cache lives

| Profile | Backing | Location | On close |
|---------|---------|----------|----------|
| Normal (`Browser::new_normal`) | Disk + in-memory index | `<profile>/network-cache/` | LRU state flushed; entries survive restarts |
| Private (`Browser::new_private`) | Memory only | none | cleared by `NetworkService::shutdown` |
| CLI `Engine` / tests with no `cache_dir` | Memory only | none | kept until drop (persistent) or cleared (private) |

`NetworkServiceConfig::cache_dir` is only used when `persistent_cache` is true. A private service ignores it, so a private profile never writes cache files even if misconfigured (`wave_e::private_profile_cache_never_touches_disk_and_is_gone_after_shutdown`). If the directory cannot be opened, the service logs a warning and falls back to a memory cache.

Normal browser profiles use a 256 MiB total / 16 MiB per-entry budget; the library default is 64 MiB / 8 MiB.

## Disk layout

```text
network-cache/
  objects/<name>.body   response body (decoded bytes)
  index/<name>.json     record: format version, method + URL key, status, headers,
                        Vary names and request values, freshness, validation flags,
                        TLS facts, last access time, body length
```

- `<name>` is generated by the cache (time, process id and a sequence number). It is never derived from the URL, so a URL cannot choose a file path.
- Writes are atomic: `*.tmp` followed by `rename`.
- Bodies stay on disk; only metadata is kept in memory. A lookup reads the body from `objects/`.
- On open, the cache drops index records with the wrong format version, a body whose size does not match the record, mismatched `Vary` data, unparseable JSON, orphaned bodies and leftover `*.tmp` files. A disk read that fails later is counted in `CacheStats::disk_errors` and the entry is dropped, never served.
- `Set-Cookie` / `Set-Cookie2` are removed before an entry is stored, in memory and on disk, and a 304 cannot add them back. Cookies are owned by `CookieService` alone (`cache::tests::set_cookie_is_never_stored_in_memory_or_on_disk`).
- The cache key is the method plus the URL without its fragment. Index records therefore contain full URLs, including query strings, like browsing history does. The directory is inside the profile and is removed with it.

## Cache key and variants

One key can hold several variants selected by `Vary`. `Vary: *` is never stored. Request header values named by `Vary` are normalised (whitespace collapsed) before comparison.

## What is stored

A response is stored only if all of these hold (`cache::is_storable`):

- method `GET`, status not `206`, no `Range` request header;
- neither the request nor the response has `no-store`;
- `Vary` is not `*`;
- freshness is understood: `max-age`, `Expires`, `no-cache`, or heuristic freshness (a `Last-Modified` on a heuristically cacheable status);
- the entry fits `max_entry_bytes` and the total budget.

## Cache states

Every `ResponseMeta` and network log entry carries a `CacheState`:

| State | Meaning |
|-------|---------|
| `Miss` | Not in the cache; fetched from the network and stored |
| `Hit` | Fresh entry served without any network request |
| `Stale` | Stale entry served without revalidation (`CacheMode::ForceCache` or `OnlyIfCached`) |
| `Revalidated` | Conditional request (`If-None-Match` / `If-Modified-Since`) answered with 304; stored body served, headers and freshness updated |
| `Bypassed` | The cache was not consulted: `CacheMode::NoStore` or `Reload`, a non-`GET` method, or a `Range` request |
| `NotCacheable` | Fetched from the network but not storable (for example `no-store`, or no freshness information) |

`CacheState::served_from_cache()` is true for `Hit`, `Stale` and `Revalidated`.

## Eviction

- Least-recently-used by an access counter; each lookup, store and 304 refreshes it.
- Eviction runs on store until the total is within `max_total_bytes`. The entry being stored is kept unless it is the only one.
- Evicting a disk entry deletes its body and index record.
- Unsafe methods (`POST`, `PUT`, `DELETE`, `PATCH`) invalidate the cached `GET` for the same URL.
- `clear()` deletes all entries and files.
- HTTP cache eviction never touches cookies, history, bookmarks or site storage. Those live in other stores.

## Persistence of recency

Last access times are kept in memory and written back to the index on `flush()`, which runs on `NetworkService::shutdown` and when the cache is dropped. After a restart the LRU order is the same as before (`cache::tests::disk_cache_keeps_lru_order_across_restart`).

## TLS facts

An entry keeps the `TlsInfo` of the response that filled it (ALPN, validated host name, certificate metadata). A hit therefore reports the security facts of the original verified connection; the negotiated protocol of a hit is `unknown`, because no connection was used. Only responses that passed certificate validation can be stored, so a restored entry is marked `certificate_verified: true`.

## Not implemented

- Shared-cache rules (`s-maxage`, `public`/`private` distinctions for shared caches). This is a private cache.
- `stale-while-revalidate` and `stale-if-error`.
- Partial-content (`206`) storage.
- A size-based background compaction task. Eviction is synchronous on store.
- Encryption at rest.
